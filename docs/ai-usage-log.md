### Key lessons

- **Verify the AI's knowledge of tools against the tools.** Spec Kit's `--ai` flag had been renamed
  (`--integration`); the .NET 8 rate limiter has no `TimeProvider` hook; `dotnet list package
  --vulnerable` exits 0 even with findings. Each was caught by running the tool, not by trusting the answer.
- **The full test suite catches what the plan misses.** A task order that broke 26 tests (a property
  mapped before its column existed); a flaky CI run that exposed a real logging bug; a sample file
  broken by the new rate limits.
- **Make "nothing happened" provable.** With background processing, "no click was recorded" needs a
  later marker click, not an immediate check; "today in UTC" needs a test clock in a far time zone.
- **Mutation checks beat coverage numbers.** Breaking the code on purpose showed which tests mattered;
  survivors were reported (two equivalent mutants), not hidden.
- **Check numbers the AI reports.** A coverage script double-counted files (54% instead of 98%); a
  summary count was wrong (corrected above); a test's own arithmetic violated its precondition.
- **AI is good at surfacing trade-offs; the engineer decides.** Controllers over minimal APIs,
  reclaimable expired aliases (overriding the AI's recommendation), rate limiting as the scope of the
  ambiguous scenario, a spec for the web UI and an ADR for Docker, AWS for the deployment design.
- **Shell and platform details matter.** zsh globbing, macOS lacking `timeout`, CRLF files rewritten
  with LF; a safety check rightly blocked an `rm` with an unguarded variable.

## Secure AI usage practices

- No secrets, credentials, connection strings, or real user data shared in prompts or committed.
- Every new dependency was justified and signed off by the engineer, and checked for known
  vulnerabilities (NuGet and npm gates in CI, Dependabot).
- Security-sensitive changes (input validation, the redirect path, migrations, data deletion, rate
  limiting) were flagged as high impact and signed off explicitly.
- **The agent commits only after the engineer's explicit "approve"** for that task (after build,
  format, full tests and vulnerability checks pass), and pushes only at agreed points; the engineer
  opens, reviews and merges every pull request. (An earlier version of this section said the AI never
  commits; that described the intended setup, not what happened in this session, and was corrected.)
